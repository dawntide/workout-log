## 1. 전제와 원칙

- **웹 구현 가능 기능만 다룬다.** 네이티브 전용(워치 앱, 홈 위젯, Live Activities/잠금화면 타이머, 백그라운드 기기 푸시, 진동/햅틱, HealthKit/Health Connect, Siri)은 갭으로 세지 않고 로드맵에 없다. 웹 가능 범위: 화면 내 타이머+종료음, Screen Wake Lock, 각종 계산기, 세트 타입, 회복 히트맵, 오프라인 로깅, CSV.
- **결정론 유지.** 생성형 AI 추천을 엔진에 넣지 않는다. "설명 가능·재현 가능"이 시장 차별점(진행 엔진 5종 모두 근거 미표시)이므로 M4가 이를 확장한다. LLM 활용은 M6의 MCP로 외부화한다.
- **기존 게이트 전부 유지·확장.** `lint` / `typecheck` / `lint:design`(No-Line·primitive-first·토큰) / core 유닛 / E2E / `lint:boundary`(core·apps/api) / TUI struct-동등성 / REF5 스펙 가드. **JEFIT의 교훈(업데이트마다 회귀 → 이탈)이 이 게이트들의 존재 이유**이므로, 로드맵 항목마다 회귀 스펙 추가를 DoD에 포함한다.
- **디자인 시스템 준수.** 모든 신규 UI는 V2 primitives 조합, `--v2-*` 토큰, 44×44 터치 영역, Material Symbols(웹). 14종 테마에서 동작(신규 시맨틱 색은 표면 사다리 ΔE 확인).
- **규모 표기**: S = PR 1개 수준, M = PR 2~4개, L = 설계 선행 + PR 5개 이상.

## 2. 마일스톤 개요와 순서

```
M1 현장 로깅 도구        (P1: 타이머·플레이트·세트타입)   ← 최우선, 매 세션 체감
M2 데이터 폭             (체중 시계열·RIR)                ← M1-3의 통계 단일화에 의존
M4 판정 근거·로드맵 공개  (차별화 1·2)                     ← 엔진 컨텍스트가 신선할 때
M3 운동 DB 오픈 카탈로그  (콘텐츠)                         ← M5의 선행 조건
M5 근육 신선도 시각화     (차별화 3)                       ← M3의 근육 매핑 확장에 의존
M6 공개 API / MCP        (차별화 4)                       ← 기능 표면이 안정된 마지막에
```

권장 착수 순서: **M1 → M2 → M4 → M3 → M5 → M6**. M4는 M2와 순서 교환 가능(상호 의존 없음). 각 마일스톤 말미에 "TUI 후행분 소화" 슬롯을 둔다.

## 3. M1 — 현장 로깅 도구 (P1)

벤치마킹 결론 1: 로깅 속도의 공식은 "프리필 + 이전 기록 인라인 + **체크 1탭 → 타이머** + 화면 안 히스토리". 우리는 마지막 고리(타이머)와 보조 도구 2종이 없다. 조사한 12개 앱 전원이 셋 다 갖췄다.

> **단위 구현계획 작성 완료** (2026-08-19) — 아래 3항목은 각각 계획서로 전개됐고, 그 과정에서 이 절의 사실 몇 가지가 실측으로 교정됐다(각 항목 머리에 표시).
> [`rest-timer-plan.md`](rest-timer-plan.md) · [`plate-calculator-plan.md`](plate-calculator-plan.md) · [`set-type-plan.md`](set-type-plan.md)

### M1-1 웹 휴식 타이머 — ~~규모 M~~ → **규모 L** ([계획서](rest-timer-plan.md))

> **교정**: 세트 완료라는 상호작용 자체가 없었다(`✓`는 `aria-hidden` 표시 전용). `✓`를 탭 버튼으로 승격하는 작업이 선행되면서 PR 5개 규모가 됐다.

- **배경**: **웹·TUI 양쪽 다 부재**(2026-08-19 코드 실측). ⚠️ 인벤토리 초판의 "TUI에 휴식 게이지 있음"은 **오류** — `apps/tui/README.md:95`에만 적힌 미구현 기능이고 대응 구현 커밋이 없다(`휴식`/`gauge`/`elapsed` grep 0건). 웹도 `restTimer|vibrate|AudioContext` 0건. 즉 **양쪽 다 신규 구축**이며, README 문구도 이 마일스톤에서 실제와 맞춘다.
- Strong = 운동별 프리셋 + 체크 시 자동 시작, Liftosaur = 세트별 처방 시간. REF5/Asymptote 문서에는 이미 세션 성격별 권장 휴식(60–90초 / 2–3분 / 3–5분)이 정의돼 있으나 UI로 구동되지 않는다 → **"처방 구동형 타이머"가 우리식 차별화**.
- 선행 이력: 폐기된 `/workout/log/keypad`(빠른 기록)에 타이머가 있었고, `web/docs/v2-next-pr-plan.md` §B3("휴식 타이머 햅틱/사운드", default 3분 전제)이 미착수 백로그로 남아 있다. **B3는 이 항목이 대체·종결**한다(햅틱·푸시는 전제 §1에 따라 범위 밖).
- **목표 UX**:
  - 세트 완료 체크 → 하단 고정 필(경과/목표, 예 `00:14 / 03:00`) 자동 시작. 탭하면 확장 시트: ±15s/±30s 조정, Skip, 남은 시간 크게.
  - 목표 시간 결정 우선순위: ① 세션/세트 처방(`restSeconds`) → ② 운동별 프리셋(설정) → ③ 전역 기본값(예 90s). 웜업 세트용 별도 기본(Strong 패턴)은 M1-3 이후 활성.
  - 종료 시: 화면 내 강조 + 짧은 사운드(첫 상호작용 후 AudioContext 언락). **백그라운드 푸시·진동은 하지 않는다**(전제 §1). 보완으로 설정에 "기록 중 화면 꺼짐 방지"(Screen Wake Lock API, 로깅 화면 한정, 기본 off).
- **터치 포인트**:
  - web: 타이머 상태 atom + 필/시트 컴포넌트(V2 primitives), 세트 완료 핸들러 연결, 설정 화면 항목.
  - settings: `SETTINGS_KEYS`에 타이머 전역 기본·운동별 프리셋·wake lock 토글 추가 (core 순수부 normalize + web DOM 어댑터 — 기존 workout-preferences 구조 따름).
  - program DSL: 세트/세션 처방에 **additive optional `restSeconds`** — program-dsl zod 스키마에 optional 필드로(⚠️ 경계는 캐스트: strict parse가 미지 형태를 통째 드롭하지 않게 기존 컨포먼스 방식 유지). REF5 프로토콜 문서의 휴식값을 seed 정의에 반영.
  - TUI: `restSeconds` 필드 수용(스키마 동시). TUI 게이지가 이 값을 쓰도록 소스 통일은 후행 가능.
- **함정**: 타이머는 `setInterval` 카운트가 아니라 **timestamp 차이로 계산**(iOS 백그라운드 스로틀 대비). SW는 `/api` 캐시 안 하는 정책과 무관(순수 클라). 오디오는 자동재생 정책 때문에 반드시 사용자 제스처 후 언락.
- **DoD**: 체크→자동 시작 / 프리셋 CRUD / REF5 세션에서 처방 시간 반영 / 타이머 라이브 리전(a11y) / E2E 1시나리오(체크→필 표출→skip) / 14종 테마 확인.

### M1-2 플레이트 계산기 — 규모 M ([계획서](plate-calculator-plan.md))

> **교정**: "자중 종목만 숨김"으로는 부족하다 — 자중 판정 함수가 풀업·친업만 잡고 카탈로그에 장비 필드가 없어 덤벨·케이블 종목에도 계산기가 뜬다. **운동 카탈로그에 장비 필드를 추가**하는 선행 PR이 범위에 들어왔다(코드 상수만, DB 컬럼 없음). 진입점은 세트 행이 아니라 **운동 카드 + 세트별 분해 시트**로 확정(램프 처방을 한 번에 커버, 5열 그리드 불변).

- **배경**: 부재(최소 원판 증분 설정·`roundToNearest2p5`·REF5 MICRO 1.25 토글만 존재). Strong(PRO)·Hevy·Liftosaur(보유 원판 정의)·Boostcamp(세트별 표시)·Alpha(조립 불가 시 차선 무게 제시) 전원 보유. **라운딩 엔진이 이미 있어 표시 계층만 얹으면 되는 최저비용 항목**.
- **목표 UX**:
  - 세트 행/운동 카드의 무게 옆 아이콘 → 시트: 바 무게 + 사이드별 원판 분해(예 `20kg bar + 20·10·2.5 / side`).
  - 설정: 바 무게(기본 20kg, 운동별 오버라이드 여지), 보유 원판 인벤토리(기본 25/20/15/10/5/2.5/1.25). 인벤토리로 조립 불가한 처방이면 "가장 가까운 조립 가능 무게" 병기(Alpha 패턴).
  - 자중 종목(bodyweight-load 판정 재사용)은 아이콘 숨김.
  - (연계) 기존 "최소 원판 증분" 설정과의 관계: 인벤토리에서 최소 증분을 유도할 수 있으면 설정 화면에서 두 값의 정합 안내. 강제 통합은 하지 않는다(기존 종목별 규칙 — 예 Pull-Up 1.25kg — 유지).
- **터치 포인트**: core 순수 lib `plate-breakdown`(greedy 분해 + 조립 가능성 판정 — 유닛/골든 픽스처), settings 확장, web 시트 UI. TUI 후행(텍스트 분해 표시는 저비용이라 마일스톤 말미 슬롯).
- **DoD**: 순수 함수 유닛(마이크로 1.25 경계·조립 불가·비대칭 인벤토리) / 시트 UI / 자중 종목 숨김 / 테마 확인.

### M1-3 세트 타입(웜업·실패) + e1RM 계산 단일화 — 규모 L ([계획서](set-type-plan.md))

> **교정 3건**: ① e1RM 중복은 4곳이 아니라 **11곳**이고 그중 3곳은 **공식이 서로 다르다**(1렙 특례·15렙 클램프·무가드) → 아래 "출력 불변" DoD는 성립하지 않으며, 특례를 표준으로 승격해 수치 변경을 수용하기로 확정. ② `validateExportShape`는 세트 필드를 검증하지 않으므로 **"갱신 필수"는 오류**(변경 불필요). ③ 저장 위치는 **additive 컬럼 `set_type`**으로 확정(볼륨 집계가 SQL 7곳이라 jsonb는 인덱스를 못 탄다). REF5는 세트 타입 **비활성**(canonicalizer의 세트 수 엄격 일치를 건드리지 않는다).

- **배경**: 부재(`isExtra`·`meta`·note 표기만). Strong 패턴이 표준: 세트 번호 탭 → Warm-up/Failure 태그, **웜업만 통계·차트 제외**. 이것은 입력 편의가 아니라 **e1RM·볼륨·진행 판정의 정확도 문제**다(웜업 세트가 볼륨을 오염시키는 현재 상태의 교정). 드롭세트는 비채택(§8).
- **선행 리팩터 M1-3a — e1RM 단일화**: Epley 계산이 4곳에 복제돼 있음(`home-service` / `stats/bundle-service` / `asymptote-monitor` / `personal-records`). 세트 타입 필터를 4곳에 각각 꽂는 대신 **core에 단일 e1RM/집계 입력 필터 함수로 통일**하고 4곳이 이를 소비하게 한다. (부수 효과: 향후 1RM 공식 선택이 열림 — 로드맵 외 후보.)
- **목표 UX**:
  - 세트 행의 세트 번호(또는 좌측 마커) 탭 → `W`(웜업)/`F`(실패) 토글 메뉴. 행에 글리프·색 토큰으로 표시(터미널 미학 정합: `[W]`류 텍스트 태그 허용).
  - 통계 규칙: 웜업 = e1RM·볼륨·PR·근육군 볼륨·진행 판정 입력에서 **제외**. 실패 = 포함하되 진행 reducer에는 "실패" 신호로 전달(기존 `isFailure` 시각 표시와 정합).
  - 프로그램 생성 세션의 웜업 처방(향후)과 수동 태그를 같은 필드로 수렴.
- **스키마/데이터 계약** (단위 계획에서 확정할 결정 2개):
  - 저장 위치: `workout_set.meta` JSON 확장 vs additive 컬럼 `set_type`. 판단 기준 — 통계 쿼리가 서버측 필터를 쓰는지(컬럼 유리) vs 전량 로드 후 계산인지(meta 무방).
  - export: JSON export에 필드 additive 반영(version 1 유지 가능 여부 검토), CSV에 `setType` 컬럼 추가. **import validator(`validateExportShape`) 갱신 필수.**
- **TUI**: 데이터 계약 변경이므로 **동시** — 직렬화 수용 + today 버퍼 표시 + 태그 입력 키(예 `t`). struct-동등성 테스트 갱신.
- **함정**:
  - REF5 판정창이 세트를 읽는 경로에서 웜업 제외 시 **REF5 스펙 문서 동반 갱신 필수**(스펙-코드 가드 #632가 강제).
  - 진행 이벤트 replay(`PATCH /api/logs/[logId]` 재계산 경로)에서 과거 로그(타입 없음)와 신규 로그의 혼재 — 타입 없음 = 기존 동작(전부 포함)으로 후방 호환.
  - 마이그레이션은 dev/prod 스키마 2벌 + CI 최종 게이트(멀티유저 격리 작업의 함정 목록 참조).
- **DoD**: reducer 유닛(웜업 무시·실패 신호) / e1RM 단일화 후 기존 수치 골든 비교(출력 불변 — 타입 미사용 데이터에서) / E2E(태그 → 통계 반영) / TUI 동등성 테스트 / CSV·JSON 왕복.

- **배경**: Liftosaur 선례(REST API+MCP 서버+AI 프롬프트 생성기). 우리는 TUI용 Bearer 토큰 인증(`auth_session` 통일 토큰)과 Hono 59 엔드포인트가 이미 있어 **기술 거리가 짧다**. "데이터는 사용자 것" 포지션(export 개방성)과 정합. 개인 도구이므로 공개 범위 = 본인 발급 토큰뿐.
- **단계**:
  1. **PAT(개인 액세스 토큰)** — 규모 M: 설정 > 계정에 토큰 발급/폐기 UI. `auth_session`과 구분되는 토큰 종류(prefix 구분, 만료 선택, 스코프 `read` / `read+write`). apps/api Bearer 수용 경로에 토큰 종류 판별 추가. 세션 목록 화면에 발급 토큰 병기. rate limit 기존 체계 재사용.
  2. **공개 API 표면 확정** — 규모 M: 59개 중 공개 서브셋 선별(logs 읽기/쓰기, stats 읽기, plans 읽기, exercises 읽기 — auth·ops·마이그레이션 제외). OpenAPI 스펙 문서 생성(수기 or hono 스키마 기반), `docs/api/` 게시. **route-order 스냅샷 테스트로 공개 표면 고정**(프로덕션 프로브로 라우트 검증 불가 — 메모리 참조).
  3. **MCP 서버** — 규모 M: 신규 패키지 `apps/mcp`(stdio, PAT 사용, 공개 API 호출 래퍼). 도구: 세션 조회/기록, 통계 요약, 플랜 상태, 프로그램 미리보기(M4-2 시뮬레이션 재사용). LLM 활용은 여기로 전부 외부화(엔진 결정론 유지).
- **함정**: PAT는 비밀번호 변경/전 세션 무효화 시 처리 정책 결정 필요(폐기 vs 유지). prod의 env 인증 fallback 차단 유지. write 스코프의 저장 멱등성 계약(요청 해시)을 API 문서에 명시. apps/api `lint:boundary` 준수(next/react 금지).
- **TUI**: PAT를 TUI 로그인 대안으로 수용 가능(스키마 동시 — 토큰 판별이 서버측이므로 TUI 변경은 선택).
- **DoD**: PAT 발급→API 호출→폐기 E2E / 스코프 위반 401·403 유닛 / OpenAPI 문서 / MCP 도구 스모크(로컬).
